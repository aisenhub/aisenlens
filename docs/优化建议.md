# AisenLens 全项目工程优化执行计划

**Agent 执行版 · V1.1（Web 优先版）**

仓库：aisenhub/aisenlens  
基线日期：2026-09-03  
适用范围：Web 主产品、Scene Engine、Supabase、工程化与文档治理

当前明确不在执行范围：Desktop、Mobile、开源/License 治理

> **文档用途**
> 这不是愿景文档，而是一份可以直接交给编码 Agent 执行的分阶段重构与优化计划。每个阶段均包含目标、边界、实施步骤、验收标准和回滚要求。除明确注明外，不允许跨阶段同时大规模修改。

# 0. 使用说明与执行纪律
本计划的核心策略是：先建立可回归的工程护栏，再解耦运行时依赖与大型组件，最后完成 Web 性能、文档治理与全量发布收口。当前阶段只优化 Web 主产品与其直接依赖，不开展 Desktop/Mobile 产品化，也不进行开源/License 治理。所有改动都必须保持现有用户数据兼容、AisenShot 生产基线稳定，以及 Web 主产品可持续发布。

## 0.1 Agent 的工作方式
- 一次只执行一个 Phase；一个 Phase 可拆成多个小 PR/提交，但不得把后续阶段的架构改动顺手混入。

- 每个 Phase 开始前先读当前代码和 package.json，不依据本计划猜测脚本名、路径或最新实现；本计划规定的是目标与边界。

- 每个提交必须可构建、可回滚；禁止“大爆炸式”同时迁移状态、存储、UI 和 Scene Engine。

- 优先“抽取并保持行为”，再“改变实现”；重构提交和行为变更提交应尽量分开。

- 发现计划与代码现实冲突时，以代码真相和测试为准，记录差异后采用最小安全修正，不擅自扩大范围。

- 所有 IndexedDB schema/数据结构改动必须有 migration verification；所有自动分镜生产配置改动必须视为产品版本变更，而不是普通重构。

## 0.2 每个 Phase 的固定输出
| **输出** | **最低要求**                                                                                |
|----------|---------------------------------------------------------------------------------------------|
| 代码     | 仅包含本 Phase 目标相关改动；目录和命名遵循现有 feature-first 结构。                        |
| 测试     | 新增/更新与改动对应的单元、集成或 verification 测试。                                       |
| 验证记录 | 记录 lint/build/test/Scene Engine verification 等结果；脚本名以仓库当前 package.json 为准。 |
| 文档     | 若架构、数据模型、运行依赖、公共 API 或发布流程变化，更新对应 docs。                        |
| 回滚点   | 保留可单独 revert 的提交边界；数据迁移必须说明降级/兼容策略。                               |

# 1. 当前基线与问题定义
AisenLens 当前已经不是简单的 React 页面集合，而是一个 local-first 视频分析工作台：Web 负责当前产品与交互，Scene Engine 负责自动分镜核心，IndexedDB 保存项目与分析数据，Supabase 提供登录、权益、反馈和支持等云能力。仓库虽然保留 Electron/Capacitor 壳，但它们在 Web 完全成熟之前不进入本计划的开发与验收范围。

## 1.1 当前关键结构
| **区域**                      | **当前职责**                                               | **主要风险/结论**                                           |
|-------------------------------|------------------------------------------------------------|-------------------------------------------------------------|
| apps/web                      | 主产品、项目管理、编辑器、媒体、导出、标定、账号与营销页面 | 产品主体；需要从大型编排组件继续解耦。                      |
| packages/scene-engine         | TS Client + Worker + WASM Runtime + C ABI + C++ detectors  | 技术成熟度最高，应保护而不是重写。                          |
| IndexedDB / projectRepository | 项目、镜头、截图、标注、自动分镜任务、恢复快照等           | 数据价值高；迁移必须保守，repository 体积过大。             |
| Supabase                      | Auth/Profile/Entitlement/Feedback/Support                  | 当前静态依赖影响完全离线启动，应变成可选 Cloud Capability。 |
| apps/desktop / apps/mobile    | 未来跨平台壳                                               | 当前冻结，不进入本轮优化、验收或发布门；待 Web 成熟后另立计划。 |

## 1.2 已确认的主要技术债
- EditorWorkspace.tsx 约 143 KB，已成为 God Component：播放、镜头、时间线、截图、分析、音轨、构图、自动分镜、标定、导出、历史和保存等职责集中。

- projectRepository.ts 约 44 KB，虽然 repository 边界正确，但内部职责需要拆分并保留 facade。

- Supabase client 在缺失环境变量时会阻断启动，“项目/视频本地”尚未等于“产品可完全离线启动”。

- Web 通过 alias/相对路径进入 scene-engine 的 src，package API 边界被绕过。

- 架构文档存在代码领先文档的漂移；IndexedDB 版本、Auto-shot 控制面等信息容易过期。

- 仓库具备大量验证脚本，但缺少强制 CI 门，需要把构建、测试、数据迁移与 Scene Engine 契约变成自动化硬门。

# 2. 全局架构红线（所有阶段必须遵守）
> **红线 A：AisenShot production v1 不得在重构中被“顺手优化”**
> general（通用/影视）与 short-form（短视频）的 production v1 预设、canonical hash、候选 review→确认→正式镜头语义、provenance、强媒体身份、checkpoint/resume 等均视为稳定产品契约。任何算法参数变化必须走独立版本与质量验收。

> **红线 B：用户项目数据不可因重构丢失**
> IndexedDB schema、对象 store、恢复快照、镜头 ID、截图引用、媒体身份、标定数据和导出输入均属于兼容面。删除字段或重命名 store 前必须有迁移与回归证据。

> **红线 C：当前只做 Web，不做 Desktop/Mobile**
> 本轮计划不得修改 Desktop/Mobile 产品能力、原生桥接或发布流程，也不得把跨平台适配作为任何 Phase 的验收条件。若为了 Web 解耦需要建立平台抽象，只实现 Web 版本并保留未来扩展接口；Electron/Capacitor 实现必须留到 Web 成熟后的独立计划。

> **红线 D：不在全局 Store 中放大型媒体对象**
> Blob、File、Worker、WASM runtime、候选大数组、checkpoint payload 等不得迁入 Zustand。Zustand 只承担真正的跨页面/跨功能轻量状态。

> **延期项（不属于当前 Phase）**
> Desktop/Electron、Mobile/Capacitor 的产品化、平台适配、能力矩阵与发布流程全部延期到 Web 完全成熟之后；仓库是否公开、License、CONTRIBUTING/SECURITY 等开源治理也不属于本计划。Agent 不应主动处理这些事项。

# 4. Phase 0 — 基线冻结与变更护栏
## 4.1 目标
在任何结构性重构之前，把“现在能工作什么、数据是什么、性能大致如何”固化成可重复验证的基线。Phase 0 不追求架构美化，只建立后续变更的安全网。

## 4.2 实施任务
- 盘点并记录根 package.json、apps/web/package.json、packages/scene-engine/package.json 现有 lint/build/test/verify/benchmark 脚本，形成唯一验证清单。

- 记录当前 Web 生产构建的主要 chunk 体积、编辑器入口 chunk、WASM baseline/SIMD 资源大小和构建警告。

- 冻结 IndexedDB 当前版本、store 列表、关键索引和 migration verification；新增一份 machine-readable schema baseline（JSON/TS 常量均可）。

- 冻结 Auto-shot production catalog v1 的 preset id/version/canonical hash，并把它作为 CI 回归 fixture。

- 选取至少 1 个真实或可分发的本地测试项目作为“编辑器恢复/保存/导出”基线；敏感媒体不可提交仓库时，仅提交 manifest 和生成说明。

- 记录关键用户旅程：新建项目→绑定视频→手工镜头→自动分镜→候选应用→刷新恢复→导出。后续 Phase 不得破坏该链路。

## 4.3 建议新增文件
```text
docs/engineering/BASELINE.md

docs/engineering/ARCHITECTURE_GUARDRAILS.md

apps/web/test/fixtures/architecture/production-contract.json # 名称可调整

apps/web/test/project-schema-baseline.verification.ts # 若现有 migration test 可扩展则不重复
```

## 4.4 验收标准
- 所有现有验证脚本在未改行为的主线基线通过，失败项必须先记录为“已知失败”，不能在后续被误认为重构引入。

- IndexedDB、production presets、核心用户旅程都有可机器验证或至少明确可复现的基线。

- Agent 后续可以仅通过文档和脚本判断“是否破坏了稳定契约”。

# 5. Phase 1 — CI 与工程质量门
## 5.1 目标
把仓库已经存在的大量验证能力接入持续集成，让“能构建、能测试、Scene Engine 可用、数据迁移可用”成为主分支的硬门，而不是开发者记忆。

## 5.2 CI 分层建议
| **Job**           | **内容**                                                          | **触发策略**                                      |
|-------------------|-------------------------------------------------------------------|---------------------------------------------------|
| web-quality       | install → lint → type/build → Web unit/verification tests         | 所有 PR；Web/共享配置变化时必须运行               |
| scene-engine-ts   | scene-engine TS tests、worker protocol、SIMD parity、WASM runtime | scene-engine、auto-shot 或构建配置变化            |
| scene-engine-core | CMake/C++ tests、ABI smoke/ABI parity                             | C++/CMake/ABI 变化                                |
| data-contract     | IndexedDB migration verification、production preset hash contract | 所有涉及 projectRepository/auto-shot config 的 PR |
| web-build-preview | 生产构建 + 必要的 wasm 资源/preview verification                  | 合并前或主分支；可按成本选择条件执行              |

## 5.3 具体任务
- 新增 .github/workflows，使用 pnpm lockfile 严格安装；Node/pnpm 版本以仓库 mise/packageManager 配置为准。

- 缓存 pnpm store，但不得缓存构建产物作为通过依据。

- 将 ESLint --max-warnings=0 保持为基础静态门；react-hooks/exhaustive-deps 暂按仓库现状处理，不在本阶段一次性升级导致大量无关修改。

- 增加 no-restricted-imports 或自定义检查，为后续 Scene Engine public API 收口做准备；Phase 6 之前可先 warning/报告，Phase 6 后转 error。

- 对 production preset hash、IndexedDB migration、Worker protocol 这类“协议型”测试设置明确失败提示，便于 Agent 识别这是契约破坏。

- 在 CI 输出 bundle size 摘要，不立刻把 500 kB 阈值设为阻断；Phase 8 完成后再设预算。

## 5.4 验收标准
- 任意 PR 都能自动判断 Web 是否可构建、基础测试是否通过。

- Scene Engine C++/TS/WASM 关键验证不再依赖手工执行。

- IndexedDB migration 和 production Auto-shot contract 破坏会直接阻止合并。

- CI 时长可接受；昂贵的浏览器/benchmark 验证可分层到主分支或标签触发。

# 6. Phase 2 — Offline-first：Supabase 变为可选 Cloud Capability
## 6.1 目标状态
没有 VITE_SUPABASE_URL / anon key、没有网络、Supabase 暂时不可用时，AisenLens 仍可启动并进入本地核心流程：项目库、视频绑定、编辑、自动分镜、标注、保存与本地导出。只有账号、权益、反馈、支持、兑换等云功能降级。

## 6.2 推荐设计
```text
services/cloud/

capability.ts # CloudCapability / availability state

cloudConfig.ts # 读取 env，不 throw

loadCloud.ts # dynamic import Supabase implementation

supabase/

client.ts

auth.ts

profiles.ts

...

App:

Local product boot ─────────────── always available

Cloud capability initialization ─ optional / lazy / recoverable
```

## 6.3 实施步骤
- 把 Supabase 环境变量检测从“模块加载即 throw”改为配置对象：configured / unconfigured / unavailable。

- 删除 App 顶层对 Supabase client 的必需静态初始化；账号相关模块通过 lazy loader 获取 client。

- Auth/Profile store 或 service 必须能表达 guest/local 模式，且 cloud unavailable 不等于应用 fatal error。

- 导航与账号 UI 在未配置云服务时显示“本地模式”或隐藏云入口；不得弹出阻塞编辑器的错误。

- 已登录会话恢复失败时，不得影响本地项目读取；需要区分网络失败、未配置、鉴权失效三类状态。

- Feedback/Support/Redemption 等调用在 capability 不可用时提供明确可恢复错误，而不是触发未捕获异常。


## 6.4 测试矩阵
| **场景**                 | **期望**                                                     |
|--------------------------|--------------------------------------------------------------|
| Supabase env 完整 + 在线 | 现有登录/资料/权益能力保持。                                 |
| 无 Supabase env          | 应用正常启动；本地项目和编辑器可用；云入口优雅降级。         |
| env 完整但离线           | 应用正常启动；本地功能可用；云请求报告 network/unavailable。 |
| 已有 session 后离线重启  | 本地项目可用；session 恢复不能造成启动白屏。                 |
| 云服务异常响应           | 错误隔离在云功能，不污染项目/编辑器状态。                    |

## 6.5 验收标准
- 移除“缺 env 即整个产品不能启动”的行为。

- 在 Playwright/浏览器验证或至少可重复的本地流程中证明无云配置可以完成核心编辑流程。

- 云能力恢复后无需刷新整个项目数据即可继续使用账号类功能（允许用户主动重试）。

# 7. Phase 3 — EditorWorkspace 分层拆解
## 7.1 目标
把 EditorWorkspace 从“拥有所有状态与业务行为的超级组件”收敛为“编辑器页面的组合器”。此阶段是整个优化计划中风险最高、收益最大的部分，必须采取增量抽取，不允许一次性重写。

## 7.2 拆分原则
- 先按业务能力抽 hooks/controllers，再按视觉区域拆 components；不要只把 JSX 切成更多文件却仍共享一团状态。

- 状态应尽可能留在最小需要范围；真正跨编辑器领域的 session state 才进入统一 session/controller。

- 保存、历史、自动分镜、导出等副作用必须有明确 API，不允许子组件直接操作 repository、Worker 或 window 级资源。

- 保持现有 EditorWorkspace props 和 ProjectMediaGate 边界，直到内部稳定；避免同时改变上层路由/项目选择。

## 7.3 推荐抽取顺序
| **步骤** | **抽取对象**                  | **职责**                                                         | **为什么先/后**                                   |
|----------|-------------------------------|------------------------------------------------------------------|---------------------------------------------------|
| 3A       | useEditorPersistence          | 加载、dirty、autosave、saveNow、visibility/unload                | 副作用明确，已有 useEditorSaveState，风险相对可控 |
| 3B       | useShotEditor                 | shots、frame ranges、shot notes/dims、active shot、手工分割/合并 | 核心领域状态，先形成清晰 API                      |
| 3C       | useEditorHistoryController    | commit/undo/redo、snapshot 构建和恢复                            | 隔离 structuredClone 与历史边界                   |
| 3D       | usePlaybackTimelineController | 播放、seek、range、reverse、timeline zoom/selection              | 减少时间线与视频控制耦合                          |
| 3E       | useMediaWorkspace             | 截图、边界截图、波形、多音轨、媒体资源 URL                       | 把媒体生命周期集中                                |
| 3F       | useAutoShotIntegration        | control/task/review/apply/calibration bridge                     | 保持 Scene Engine/Auto-shot 不泄漏到主组件        |
| 3G       | useOverlayWorkspace           | composition/content overlays、drawing state                      | UI 高交互但相对独立                               |
| 3H       | useExportController           | 报告/XLSX/视频导出、job/progress/cancel                          | 低频功能，可同时为后续 lazy-load 做准备           |

## 7.4 建议目录（可按现有风格调整）
```text
features/editor/

components/EditorWorkspace.tsx

session/useEditorSession.ts

controllers/useEditorPersistence.ts

controllers/useShotEditor.ts

controllers/usePlaybackTimelineController.ts

controllers/useEditorHistoryController.ts

controllers/useMediaWorkspace.ts

integrations/useAutoShotIntegration.ts

controllers/useOverlayWorkspace.ts

controllers/useExportController.ts
```

## 7.5 关于历史系统的特殊处理
现阶段先“隔离”历史，而不是立刻改成复杂 command/event sourcing。把 snapshot 构建、structuredClone、上限、恢复 API 独立出来，保留行为一致；Phase 8 再基于真实内存数据决定是否引入结构共享、patch 或 command history。

## 7.6 阶段验收指标
- EditorWorkspace 不再直接包含大多数 repository 写入、Worker 生命周期、导出 job、历史 snapshot 细节。

- EditorWorkspace 目标控制在约 600–900 行的组合层；若因 UI 结构仍略大，可接受，但业务副作用必须已下沉。

- 每个抽取 controller/hook 都有清晰输入输出，能被单独测试；避免形成一个新的 useEditorEverything。

- 核心用户旅程与快捷键行为、自动保存、undo/redo、自动分镜应用、刷新恢复保持一致。

# 8. Phase 4 — projectRepository 内部分仓与数据边界
## 8.1 目标
保留 projectRepository 作为对业务层稳定的 facade，同时把 IndexedDB schema/migration 和各领域数据操作拆进内部 repository。外部调用方无需一次性迁移，降低数据层重构风险。

## 8.2 推荐内部结构

```text
features/project/services/repository/

schema.ts # version / stores / indexes

migrations.ts # versioned migration steps

projectRepo.ts

mediaRepo.ts

shotRepo.ts

screenshotRepo.ts

autoShotRepo.ts

calibrationRepo.ts

recoveryRepo.ts

backupRepo.ts

../projectRepository.ts # facade，兼容现有 import
```

## 8.3 实施规则
- 第一轮只移动实现，不改变 facade 方法签名、返回类型、transaction 语义和 store 名。

- 跨多个 store 的原子操作由 facade 或 transaction coordinator 编排，不能因为拆文件失去同一 transaction。

- migration 逻辑必须保持版本顺序和幂等边界；不需要 schema 变化时不要提升 DB version。

- 建立 repository contract tests：同一输入下，拆分前后的序列化记录、关键索引查询和删除级联行为一致。

- ProjectRecord/ShotData 等领域类型继续放在明确 types 层，避免 repository 子模块各自产生重复类型。

## 8.4 验收标准
- projectRepository facade 明显变薄，主要承担组合与兼容；子 repository 具备单一职责。

- 现有项目库、项目打开、自动保存、恢复、标定、自动分镜 task/checkpoint 等无数据回归。

- DB migration verification 覆盖从至少两个旧版本升级到当前版本（具体版本以仓库实际 fixture 为准）。

# 9. Phase 5 — Web Platform Boundary：收口浏览器平台能力
## 9.1 目标
把“选文件、持久化文件权限、重绑媒体、保存导出、能力探测”等浏览器特有逻辑从项目/编辑器业务中抽离。业务层只处理 MediaSource、MediaAsset 和抽象资源引用，不直接判断 `window.showOpenFilePicker`、下载能力或浏览器权限 API。

本 Phase **只实现 Web**。不得新增 Electron IPC、Capacitor plugin、Native picker 或移动端兼容代码。接口可以预留未来扩展能力，但不能为了未来平台增加当前 Web 不需要的复杂度。

## 9.2 建议接口
```text
interface WebPlatformMediaAdapter {
  capabilities(): WebPlatformCapabilities
  selectVideo(): Promise<SelectedMedia>
  selectAudio(): Promise<SelectedMedia>
  reopenPersistentMedia(ref: PersistentMediaRef): Promise<File | Blob>
  requestMediaPermission(ref: PersistentMediaRef): Promise<PermissionResult>
  saveFile(request: SaveFileRequest): Promise<SaveResult>
}

createWebPlatformAdapter(): WebPlatformMediaAdapter
```

## 9.3 实施步骤
- 实现 `WebPlatformMediaAdapter`，内部封装现有 File System Access API、`<input type=file>` fallback、浏览器文件保存与权限探测；对用户的现有行为保持不变。

- 将 `PersistentMediaRef` 定义为 Web 当前真实需要的数据结构，不为 Electron path/token 或 Capacitor URI/bookmark 提前设计复杂联合类型。未来跨平台阶段可在保持业务接口稳定的前提下扩展。

- `ProjectMediaGate` 改为通过 Web adapter 判断媒体是否可恢复、是否需要权限或重绑，不再直接知道浏览器 API。

- 导出文件保存服务同样走 Web adapter，使 video/xlsx/report export 不再各自操作浏览器保存能力。

- 统一 object URL、文件权限和 capability probe 的生命周期，避免散落在多个 feature 中。

- 明确 fallback 场景：浏览器不支持持久 FileSystemFileHandle 时，产品应如何提示重绑与恢复，不能依赖隐式失败。

## 9.4 明确禁止
- 不修改 `apps/desktop/**` 或 `apps/mobile/**`。

- 不实现 `ElectronAdapter`、`CapacitorAdapter`、IPC、原生文件选择或移动端保存。

- 不因为“未来可能跨平台”把当前接口抽象成过度通用的框架。

## 9.5 验收标准
- `features/project/services/mediaService.ts` 不再承担所有浏览器平台检测逻辑。

- Web 新建项目、绑定/重绑视频、权限恢复、本地保存与导出行为完全回归。

- 没有持久 handle 的 fallback 场景有明确产品行为，而不是隐式失败。

- EditorWorkspace、ProjectMediaGate 和导出领域不直接访问 `window.showOpenFilePicker` 等平台 API。

- Desktop/Mobile 目录零功能性改动。

# 10. Phase 6 — Scene Engine Package API 边界收紧
## 10.1 目标
让 packages/scene-engine 真正成为可独立版本化的内部产品包。apps/web 只能依赖 package exports，不允许跨包相对路径进入 src，也不允许 Vite alias 绕过 public API。

## 10.2 实施步骤
- 盘点 apps/web 对 packages/scene-engine/src 的所有直接/间接 import，分类为“应该 public export”和“只应在 package 内部使用”。

- 补全 scene-engine/src/index.ts 与 package.json exports，仅暴露 Client、公共 config/types/result、必要 feature probe；Worker 内部实现保持私有。

- Web import 全部改为 @aisenlens/scene-engine 或明确的 export subpath。

- 移除/调整 Vite alias 直指 src 的做法，确保 workspace package 在 dev/build/test 中都按公共边界解析。

- 增加 no-restricted-imports/architecture test：禁止 apps/\* 引用 packages/scene-engine/src 或 cpp/dist 内部路径。

- 确认 Worker URL、WASM baseline/SIMD URL 在生产构建中仍稳定；不要为了 package 收口改变运行时资源发现协议。

## 10.3 验收标准
- 仓库搜索不到业务代码跨包进入 scene-engine/src 的 import。

- scene-engine 可以单独 build/test，Web 只依赖声明的 exports。

- ABI parity、SIMD parity、Web build/preview verification 全部通过。

# 12. Phase 8 — 编辑器加载、内存与历史性能优化
## 12.1 原则
性能优化必须建立在 Phase 0 基线和 Phase 3 解耦之后。先测量，再改变。目标不是追求极小 bundle，而是降低编辑器首屏负载、长视频分析内存峰值和大型项目 undo/redo 成本。

## 12.2 优化方向
| **方向**          | **动作**                                                                                 | **验证指标**                                  |
|-------------------|------------------------------------------------------------------------------------------|-----------------------------------------------|
| 首包拆分          | 编辑器、视频导出、XLSX、标定工作台、开发者高级面板按需加载；Mediabunny/重模块动态 import | 入口 chunk 与首次进入非编辑器页面体积下降     |
| Scene Engine 加载 | 仅在启动自动分镜/能力探测需要时加载 Worker/WASM；保持缓存                                | 首页/项目库不下载 WASM；首次扫描可接受        |
| 历史内存          | 给 history 明确容量/估算；隔离 snapshot；基于 profile 决定 patch/command/结构共享        | 连续编辑 N 次内存增长可控，undo/redo 延迟稳定 |
| 媒体 URL 生命周期 | 集中 createObjectURL/revokeObjectURL；截图/波形资源按使用范围释放                        | 项目切换后无明显泄漏                          |
| 长列表/时间线     | 必要时虚拟化 shot list / screenshot list；避免不必要全量 re-render                       | 镜头数上百/上千时交互仍可接受                 |
| Worker/导出       | cancel/terminate/dispose 路径统一，项目切换与 unmount 强制清理                           | 无残留 job、后台 CPU 持续占用                 |

## 12.3 历史系统升级门槛
只有 profiling 明确显示 structuredClone snapshot 是主要瓶颈时，才进入第二阶段优化：可选择 command history、JSON patch、Immer patch 或领域级结构共享。不要为了“理论优雅”引入复杂事件溯源。任何方案都必须保留当前 undo/redo 用户语义。

## 12.4 建议性能预算
- 记录而非猜测：构建产物至少跟踪编辑器主 chunk、Scene Engine JS/WASM、XLSX/导出相关 chunk。

- Phase 8 完成后，在 CI 建立“不得无解释显著增长”的预算；阈值根据实际 baseline 设置，不在计划中硬编码一个不符合仓库现实的数字。

- 用至少一个短视频和一个较长视频验证自动分镜的峰值内存、扫描耗时和取消/恢复。

# 14. Phase 10 — 全量回归、数据验证与 Web 发布收口
## 14.1 必须覆盖的回归旅程
- 全新用户、本地模式：无 Supabase env → 新建项目 → 导入视频 → 编辑 → 自动保存 → 刷新恢复 → 导出。

- 云模式：登录/退出、session 恢复、资料/权益、云不可用降级。

- 编辑器：手工镜头、undo/redo、快捷键、截图、构图/内容 overlay、分组、音轨、视频/报告/XLSX 导出。

- 资源清理：项目切换/关闭编辑器后 Worker、video export job、object URL、timer、audio context 等均释放。

- 生产构建：Web 构建、预渲染、WASM baseline/SIMD 资源、Vercel/静态部署行为保持。

## 14.2 发布前 Go / No-Go
| **检查项** | **Go 条件**                                    | **No-Go**                            |

| 性能       | 无明显退化，目标指标有记录                     | 内存/首包/扫描显著恶化且无解释       |
| CI         | 主分支所有硬门通过                             | 存在被跳过的关键验证                 |
