# 拉片产品与开源生态调研报告

## 1. 调研结论

本次调研重点覆盖以下几类内容：

- 中文语境中的“拉片 / 电影拉片 / 短视频拉片 / 影片分析”
- Shot-by-shot analysis
- Shot boundary detection
- Movie scene segmentation
- Video annotation
- Long-video understanding
- Cinematic shot analysis
- 与拉片直接相关的开源项目
- 拉片依赖的底层开源能力，包括镜头切分、字幕/ASR、OCR、视觉理解、场景分组、声音分析、时间轴标注与导出

核心判断是：

> **真正好的拉片产品，不应该是“上传视频 → AI 给你一份报告”。**

更合理的产品形态应该是一个：

> **Video Understanding IDE / 视频理解工作台**

它的基本流程应该是：

> **视频 → 自动建立时间索引 → 镜头 → 场 → 段落/剧情线 → 逐层分析 → 人工校正 → 提炼规律 → 转化成自己的创作资产 → 沉淀进案例库**

其中最重要的原则是：

> **机械工作尽可能自动化，判断工作由 AI 辅助，人保留最终解释权。**

---

## 2. 用户核心痛点

目前最集中的痛点，并不是“不知道什么叫景别”，而是：

> **拉片前 70% 的时间浪费在没有学习价值的机械劳动上。**

有实际使用者描述，为了拆解一部电影，仅“逐秒截图、抄字幕、对齐时间码”就可能花掉数个晚上。短视频场景也类似，一条一分钟级视频，传统“截图 → 时间轴 → 节奏 → 总结”的完整过程可能耗时数小时。

综合来看，用户痛点主要集中在以下几个方面：

| 痛点 | 现在为什么难 | 真正应该解决什么 |
|---|---|---|
| 机械操作太多 | 暂停、截图、命名、时间码、字幕复制、建 Excel | 全自动建立素材索引 |
| 镜头切分不可靠 | 闪光、快速运动、摇镜会误切；淡入淡出、叠化容易漏切 | 自动切分 + 置信度 + 人工极速修正 |
| 字幕不准或不同步 | ASR 时间码误差、不同版本字幕错位 | 强制对齐到时间线 |
| 只看到镜头，看不到结构 | 一张几百行表格无法表现剧情线、场、段落、情绪 | 层级化结构 |
| AI 容易说套话 | “营造紧张氛围”“增强代入感”可套用到大量镜头 | 所有结论必须绑定证据 |
| 分析“是什么”，不解释“为什么” | 景别、运镜只是标签 | 分析叙事功能和观众效果 |
| 拆完无法复用 | 最终只留下 PDF / Excel | 变成可以搜索、比较、调用的知识资产 |
| 长片 AI 成本巨大 | 两小时电影不适合直接整体送入模型 | Coarse-to-fine 渐进式分析 |
| 不同用户目标不同 | 电影学生、剪辑师、广告人、短视频作者关注维度不同 | 先定义分析目标，再决定分析 Schema |
| 画面被分析，声音被忽略 | 单张关键帧无法体现节奏、BGM、音桥、停顿 | 视觉 + 语言 + 声音联合时间轴 |

因此：

> **“自动切镜准确率很高”绝不意味着拉片产品已经完成。**

镜头切分只是拉片流程的最底层基础设施之一。

## 3. 开源生态中的关键项目

### 3.1 直接面向“拉片”的项目

| 项目 | 主要能力 | 值得借鉴的地方 |
|---|---|---|
| Lapian Notes | 本地抽帧、字幕、AI 分析、剧情泳道、结构树、情绪曲线、段落深拆 | 产品思路比较接近正确方向：**全局粗拆 → 局部深拆**，同时强调 local-first |
| video-ai-analysis | 播放器、镜头检测、逐帧、时间码、多种 AI 分析视角 | 拉片工作台 UI 的较完整参考 |
| video-shot-analysis-feishu | 自动切镜 → 逐镜头分析 → 生成提示词 → 飞书 Base | 非常重要的思想：**拉片结果不是报告，而是数据库和生产资产** |
| short-video-shot-analysis | 爆款机制、叙事、情绪、镜头、剪辑、创作模板 | 将“分析”进一步转化为“可复用方法论” |
| tonychanfilms 拉片工具 | 播放、时间点、截图、结构化笔记、导出 | 非 AI 场景下基础交互逻辑的参考 |
| video-prompt-workbench | 参考视频 → 抽帧 → 视觉分析 → 反推镜头/视频 Prompt | 对 AI 视频时代尤其重要：完成“分析 → 生成”的闭环 |
| ShotTransformer | 自动识别景别、角度、镜头运动 | 说明专业影视标签可以由专用模型处理，而不是全部交给 LLM |

## 4. 拉片所依赖的底层开源能力

拉片本质上可以理解为：

> **一个多模态视频 ETL + 人机协同理解系统。**

关键能力可以拆成以下几层：

| 能力层 | 代表开源项目 | 在拉片中的用途 |
|---|---|---|
| 镜头切分 | PySceneDetect | 硬切、阈值、Adaptive Detector，工程成熟 |
| 神经网络切镜 | TransNetV2 | 补充传统检测器对复杂转场的处理能力 |
| 场景级分组 | SceneSeg / LGSS | 将 shot 进一步组织为 scene |
| 电影结构数据模型 | MovieNet | 提供 frame → shot → thread → scene → movie 的结构思路 |
| ASR | Whisper / faster-whisper | 提取台词 |
| 精确字幕对齐 | WhisperX | Word-level 时间戳、说话人区分 |
| 画面文字识别 | PaddleOCR | 字幕、标题、UI、商品文案等 |
| 长视频理解 | MovieChat | 长片全局语义和上下文压缩 |
| 音视频多模态理解 | Video-LLaMA | 联合分析视频与音频 |
| 视频标注交互 | CVAT / VideoAnnotator | 时间段标注和人工 Review UX |
| 声音时间线 | wavesurfer.js | 波形、对白、BGM、SFX 时间轴 |
| 编辑器互操作 | auto-editor | Premiere、Resolve、FCP 等时间线导出思路 |

其中 MovieNet 的结构思想尤其重要：

> **frame → shot → thread → scene → movie**

这比：

> **video → 一堆截图 → AI 报告**

更适合作为真正的拉片产品架构。

## 5. 我认为正确的拉片流程

### 5.1 第一步：先定义“为什么拉”

产品不应该从“上传视频”开始，而应该先问：

- 学导演
- 学摄影
- 学剪辑
- 学编剧结构
- 拆爆款
- 广告分析
- AI 视频复刻
- 竞品分析
- 音乐视频分析
- 短视频节奏分析

不同目标应该对应不同的分析 Schema。

广告、剧情电影、短视频，不应该被强行塞进同一张拉片表。

---

### 5.2 第二步：建立媒体索引

视频导入后，先尽量通过本地或专用模型完成确定性处理，而不是立即调用大语言模型。

包括：

- Codec 检测
- Proxy 代理文件生成
- 音轨信息
- 字幕轨
- 帧率
- 视频时长
- 文件 Hash
- ASR
- OCR
- 音频波形
- 镜头边界
- 候选关键帧

这一层应该尽量 Deterministic。

---

### 5.3 第三步：建立 Shot Timeline

使用 PySceneDetect、TransNetV2 等方式自动建立镜头时间线。

每个镜头边界都应该带有：

- 时间码
- 置信度
- 转场类型
- 前后关键帧

同时用户应该可以通过非常低成本的操作完成：

- 合并前后镜头
- 在当前点切开
- 拖动边界
- 忽略误识别

这一点非常重要。

如果切镜错误直接进入后续 AI 分析，一个错误边界会持续污染后续：

- 镜头分析
- 场景分组
- 节奏分析
- 结构判断
- AI 总结

因此必须设计一个“人工极速校正层”。

---

### 5.4 第四步：Shot → Scene → Sequence / Beat / Thread

产品的数据结构不应该停留在镜头。

至少应该支持：

> **Film → Sequence → Scene → Beat → Shot → Frame**

同时：

- 人物线
- 剧情线
- 主题线
- 情绪线

可以作为独立 Overlay 覆盖在时间轴上。

场景的判断不能只依赖画面变化，还应结合：

- 人物
- 地点
- 时间
- 对白
- 声音
- 语义连续性
- 叙事任务

---

### 5.5 第五步：先做全片粗理解

不要一开始就让 AI 给每个镜头写长篇分析。

更合理的是先进行一次“低分辨率理解”：

生成：

- 人物列表
- 地点列表
- 主要剧情线
- 场景列表
- 关键转折
- 节奏变化
- 情绪走势
- 重复 Motif
- 核心结构节点

让 AI 先获得全片上下文。

这就是：

> **Coarse-to-fine**

即：

> **全局粗拆 → 关键段落深拆**

---

### 5.6 第六步：Scene 内再做逐镜头分析

当用户进入某个 Scene 后，再调用更昂贵、更精细的模型做逐镜头深拆。

每个 Shot 不应该只展示：

- 中景
- 推镜
- 暖色

而应该强制分成三个层级：

#### 1. 可观察事实

例如：

> 镜头从中景缓慢推至特写。

#### 2. 解释 / 作用

例如：

> 画面尺度逐渐缩小，压缩人物的心理空间，并增强观众对情绪变化的注意。

#### 3. 可迁移方法

例如：

> 当角色从隐藏情绪转向承认冲突时，可以使用持续渐近的镜头尺度变化，而不是直接切到特写，从而让心理变化获得连续性。

第三层才是真正能被创作者“学走”的东西。

---

### 5.7 第七步：所有 AI 判断必须可追溯

例如 AI 说：

> “这里建立了悬念。”

用户点击这句话时，系统应该能够直接跳转到：

- 对应时间码
- 对应镜头
- 对应字幕
- 对应关键帧
- 对应上下文

所有分析应尽量区分：

- Fact
- Inference
- Interpretation
- Hypothesis

并保留：

- 置信度
- 证据
- 人工修正

真正好的拉片产品，不应该要求用户相信 AI。

而应该鼓励用户：

> **验证、修正、反驳 AI。**

---

### 5.8 第八步：自动完成“组镜分析”

很多电影语言并不存在于单独一个镜头里。

而存在于：

> **镜头与镜头之间。**

因此 Scene 级分析应自动生成：

- 平均镜头时长
- Shot Duration 分布
- 景别序列
- 正反打模式
- 镜头尺度变化
- 剪辑密度
- 视觉轴线
- 人物 POV
- 对白密度
- BGM / SFX
- 音桥
- J Cut
- L Cut
- 重复构图
- 色彩变化
- 镜头运动变化
- 节奏转折点

这一层往往比单镜头分析更有学习价值。

---

### 5.9 第九步：把分析转换成创作资产

拉片的终点不应该是“生成报告”。

而应该允许把一份分析转换成：

- 镜头表
- Storyboard
- 剪辑节奏模板
- 导演技法卡
- 广告结构模板
- 短视频 Hook 模板
- AI 图片 Prompt
- AI 视频 Prompt
- 自己的拍摄 Shot List
- 分镜方案
- 创作参考包

这样拉片才真正完成：

> **分析 → 创作**

---

### 5.10 第十步：进入永久案例库

每次拉片最终都应该沉淀进入一个可搜索的案例知识库。

未来用户可以直接查询：

- 给我找所有“特写 → 大全景”制造反差的案例
- 找出我以前拆过的所有音桥转场
- 哪些视频使用了 3 秒内快速切镜建立 Hook
- 比较《寄生虫》和《燃烧》的空间表达
- 找出所有“人物沉默但通过镜头运动推进情绪”的案例

到这里：

> **拉片才从一次性学习行为，变成个人或团队长期积累的导演 / 剪辑知识库。**

## 6. UI 不应该继续以“大表格”为核心

很多现有工具最大的问题之一，就是把“拉片数字化”理解成：

> **把 Excel 搬到网页里。**

但表格适合导出，不适合理解电影。

更合理的 UI 应该至少分成三个层级：

| 层级 | UI | 解决的问题 |
|---|---|---|
| Overview | 全片结构地图 / 剧情泳道 / 情绪与剪辑密度曲线 | 整部片是怎么组织起来的？ |
| Scene Board | 场景卡 + Shot Strip + 字幕/声音时间轴 | 这一场是怎么构造的？ |
| Shot Inspector | 当前镜头播放器 + 前后帧 + 技术标签 + AI 分析 | 这个镜头具体做了什么？ |

操作流应该是：

> **Overview 点一个高潮 → Scene 展开 → 点一个 Shot → Inspector 深看 → 随时返回上下文**

而不是：

> **Excel 第 273 行 → 第 274 行 → 第 275 行**

## 7. 一个 Shot 应该存什么

不建议做一个拥有几十个必填字段的“专业拉片表”。

更合理的方式是：

> **底层 Schema 丰富，前端根据用户目标动态展示。**

建议的 Shot 数据结构如下：

```text
Shot
├── identity
│   ├── shot_id
│   ├── start / end / duration
│   └── confidence
│
├── evidence
│   ├── keyframes
│   ├── micro_clip
│   ├── transcript
│   ├── OCR
│   └── audio waveform
│
├── cinematography
│   ├── shot_size
│   ├── camera_angle
│   ├── camera_movement
│   ├── composition
│   ├── lighting
│   ├── color
│   ├── blocking
│   └── focus / lens feel
│
├── editing
│   ├── transition
│   ├── continuity
│   ├── relation_to_prev
│   └── relation_to_next
│
├── sound
│   ├── dialogue
│   ├── ambience
│   ├── SFX
│   ├── music
│   └── audio_bridge
│
├── narrative
│   ├── what_happens
│   ├── narrative_function
│   ├── information_change
│   ├── emotion_change
│   └── audience_effect
│
└── learning
    ├── why_this_works
    ├── reusable_pattern
    ├── storyboard_prompt
    └── video_prompt
```

其中一个非常重要的产品原则是：

> **“画面发生了什么”和“为什么这么拍”绝对不能放在同一个字段里。**

否则 AI 很容易把推测包装成事实。

## 8. 哪些任务该交给 LLM，哪些不该

建议明确划分自动化边界：

| 任务 | 是否应该让 LLM 主导 |
|---|---:|
| 视频转码 | ❌ |
| 时间码 | ❌ |
| 镜头边界 | ❌，专用算法主导 |
| ASR | ❌，专用模型 |
| OCR | ❌，专用模型 |
| 景别 / 角度 | ⚠️，专用模型优先 |
| 人物 / 地点聚类 | ⚠️，CV + LLM |
| 场景分组 | ⚠️，Multimodal + LLM |
| 镜头里发生了什么 | ⚠️ |
| 为什么这么设计 | ✅ |
| 全片结构 | ✅ |
| 创作意图假设 | ✅，但必须标记为 Interpretation |
| 可复用方法论 | ✅ |
| 改编成自己的 Shot List | ✅ |

核心原则：

> **确定性任务尽量交给专用工具。**
>
> **解释性任务再交给 LLM。**

这样可以显著减少：

> “AI 看起来说得很专业，但实际上在编。”

## 9. 当前市场真正缺失的能力

现在已经有大量工具可以完成：

> **视频 → 截图 → LLM → 表格**

因此，“AI 自动拉片”本身并不是足够强的产品定义。

真正缺的是：

> **视频 → 可验证的结构化理解 → 人机共同修正 → 跨镜头规律 → 可复用创作资产**

真正有可能形成产品壁垒的不是 Prompt，也不是某一个大模型。

更可能是以下三个方面：

### 9.1 正确的视频语义数据结构

```text
frame
→ shot
→ beat
→ scene
→ sequence
→ thread
→ film
```

### 9.2 真正适合人类拉片的交互系统

```text
overview
→ scene
→ shot
```

### 9.3 越拉越有价值的个人 / 团队案例库

```text
Analyze once
→ Reuse forever
```

## 10. 第一版产品建议

如果现在做第一版，我建议主动克制功能。

第一版只跑通以下核心闭环：

> **导入视频**  
> ↓  
> **自动切镜**  
> ↓  
> **ASR / OCR**  
> ↓  
> **快速人工校正**  
> ↓  
> **自动成 Scene**  
> ↓  
> **全片结构地图**  
> ↓  
> **点 Scene 做逐镜头 AI 深拆**  
> ↓  
> **事实 / 作用 / 方法 三栏**  
> ↓  
> **一键转成创作模板**  
> ↓  
> **存入案例库**

情绪曲线、几十种统计图、复杂报表都可以后置。

第一版真正应该制造的 Aha Moment 是：

> **以前我拉一个视频要 2 小时。**
>
> **现在几分钟后，整个视频已经被摆在桌面上，我只需要思考它为什么有效。**

---

## 11. 最终产品定义

我对“拉片”的最终定义是：

> **拉片不是把视频拆成镜头。**
>
> **拉片是把成片反向编译成创作决策。**

用户真正想获得的，不是 300 个镜头标签。

而是理解：

> **导演 / 剪辑师在这里做了什么决定？**
>
> **为什么这样决定？**
>
> **产生了什么观众效果？**
>
> **以后我在什么情况下也可以这样决定？**

因此，如果要围绕拉片做一个长期产品，整个系统都应该围绕这一目标设计：

> **从“看懂视频”走向“学会创作”。**
